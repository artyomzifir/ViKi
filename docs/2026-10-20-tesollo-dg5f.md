# Tesollo DG5F на UR10: монтаж, объектный план и профиль времени (20.10.2026)

## Итог и границы результата

Для сцены `g10_object2_190` собрана правая Tesollo DG5F из [VAlikV/tesollo_dg5f_mujoco](https://github.com/VAlikV/tesollo_dg5f_mujoco), commit `783b992745cd800b339cfdde7a2ae968cb76c59d`. Локальный checkout лежит в игнорируемом `models/tesollo_dg5f_mujoco/`. Его исходные 20 суставов, визуальные меши и коллизионные STL сохранены. DAE переведены в OBJ только для загрузчиков Pinocchio/MuJoCo; сравнение границ конвертированных DAE с оригинальными STL подтвердило совпадение координат.

**Объектный план пока диагностический, физический захват не получился.** Он использует конечный оптимизированный `hand_fit` из `cln.npz`, отслеживаемый объект №2 и seed UR10 только как начальное приближение. План `tesollo_object_plan.npz` имеет `solver_status=diagnostic_unvalidated_collision`; в MuJoCo `success=false`. Эти файлы нельзя выдавать за валидированную демонстрацию захвата.

### Крепление и исправленная ошибка

Исходный MJCF крепит `rl_dg_mount` к `wrist_3_link` в `[0, 0.110, 0]` с кватернионом `[-1, 1, -1, -1]`. Первая наша версия ошибочно приняла 110 мм за длину переходника, хотя это **смещение от начала координат запястья**. Следующая диагностическая версия сократила и смещение, посадив кисть внутрь запястья. Оба варианта отозваны.

В текущем `prepare_tesollo_urdf.py` точка крепления снова находится в `Y=110 мм`. Упрощён **только переходник**: цилиндр радиусом 28 мм и длиной 10 мм между `Y=100` и `110 мм`; коллизионные меши DG5F не упрощались. Это эскизная геометрия без крепёжных отверстий, допуска и проверки изготовления. Ось DG5F `+Z` (линия mount→palm→нейтральные пальцы) после фиксированного поворота совпадает с выходной осью UR10 `wrist_3_link +Y`: скалярное произведение `1.000000`. В нейтральной позе кисть продолжает ось запястья. На кадре с планом фаланги выглядят повёрнутыми, потому что **суставы согнуты рассчитанным hand-fit**; это не угловой переходник.

Исходный UR10 в проекте и UR10e в чужом MJCF отличаются. Поэтому совпадение осей проверено на собранном нашем URDF, а производство переходника и механическую посадку на реальном фланце ещё нужно проверить отдельно.

## Куда уходит время

Один полный прогон **только текущего объектного ретаргета DG5F** на 190 кадрах, контейнер `viki-experiments`, лимит 12 CPU и 11 GiB RAM. Измерены `time.perf_counter` и `time.process_time`; начало — чтение готовых `cln.npz` и трека объектов, конец — запись плана. Захват, исходный hand-fit и сегментация уже были готовы и в эти доли не входят.

| Этап | Время, с | Доля общего wall time | Устройство |
|---|---:|---:|---|
| Загрузка входов | 0.004 | 0.01% | CPU |
| Загрузка URDF/геометрии | 0.957 | 1.08% | CPU |
| Подгонка 20 суставов к конечному human hand-fit | 16.547 | 18.74% | CPU |
| Поджим хвата по объекту | 0.056 | 0.06% | CPU |
| Инициализация IK руки по кадрам | 8.248 | 9.34% | CPU |
| Проверка пола/коллизий/границ всей траектории | **62.459** | **70.75%** | CPU |
| Проверка статуса, ретайминг, запись | 0.008 | 0.01% | CPU |
| **Итого** | **88.279** | **100%** | CPU |

Процессорное время `88.261 с` при wall time `88.279 с` показывает примерно **одно занятое логическое ядро**, то есть ~100% одного ядра, ~8.3% лимита 12 ядер или ~6.25% 16 логических CPU хоста. `docker stats` в дорогом этапе показывал около 100% CPU. Пик RSS процесса — 387.7 MiB. В списке `nvidia-smi --query-compute-apps` процесса ретаргета не было: его вычисления идут на CPU, GPU compute в нём 0. Показанные `nvidia-smi` 7% общей загрузки GPU относятся к системе целиком и не могут быть приписаны этому процессу. При отдельном GUI реплее `nvidia-smi pmon` показал у `python3` около 7% SM / 3% памяти GPU на одном снимке; это рендеринг MuJoCo, не IK. Viewer export отдельно занял 1.56 с wall time с запуском контейнера.

Бутылочное горлышко — точная проверка расстояний между множеством пар исходных коллизионных мешей на каждом кадре. Она не распараллелена по кадрам. Для ускорения сначала стоит профилировать/сокращать проверяемые пары с сохранением строгой проверки исходных STL; геометрию самой DG5F без отдельного согласования менять нельзя.

```bash
git clone https://github.com/VAlikV/tesollo_dg5f_mujoco.git models/tesollo_dg5f_mujoco
git -C models/tesollo_dg5f_mujoco checkout 783b992745cd800b339cfdde7a2ae968cb76c59d
docker compose -f docker-compose.experiments.yml build sim
# В образе viki-experiments, с data/ для записи: python3 experiments/prepare_tesollo_urdf.py
# Затем python3 experiments/hocap_tesollo_object_attempt.py --diagnostic-plan
# Затем python3 experiments/tesollo_viewer_export.py
# Из desktop-сессии с DISPLAY/XAUTHORITY: ./experiments/run_tesollo_viewer.sh --output /app/rl-output/tesollo_corrected_mount
```

Флаг `--diagnostic-plan` нужен только для осмотра случая, который строгий расчёт отклоняет. Без него генератор падает на нарушении коллизий и не пишет якобы валидный план.
